## 1. Context

profilegen generates David's portfolio site tecnologer.net.

**Authoritative flow:**

```
page/reydavid_experience.md      (hand-maintained SOURCE of truth, committed, published)
    │
    │  profilegen extract         (runs LOCALLY, never in CI)
    ▼
data/resume.yaml                  (fully machine-generated, committed, never hand-edited)
    │
    │  profilegen build           (runs locally AND in GitHub Actions on push)
    │  + template/index.html.tmpl (carries all site-only static content)
    ▼
page/index.html                   (the ONLY file build writes)
    │
    │  GitHub Actions deploy      (push to main → GitHub Pages, page/CNAME preserved)
    ▼
https://tecnologer.net
```

Two facts drive most of this document:

1. **The output directory contains the input.** `page/` holds both the
   hand-maintained source and the build output, because the site advertises the
   source as a real `curl` target. Any command that writes, cleans or regenerates
   `page/` wholesale destroys the source. Today `build.go:56-58` does exactly that
   (FR-39, FR-40), and `Makefile:21` (`make clean`) does it too.
2. **The source format is being reversed.** Revision 2 assumed the source keeps its
   machine-written KV format (`- period:`, `- roles:`, `- tags:`). David has ruled
   the opposite: the file is reformatted into a normal recruiter resume (§6). That
   reinstates tag auto-inference (§7) and drops the fields the KV format carried
   for free (§10, D-01).

The committed source file carries **no** `Generated by profilegen ... do not edit by
hand` header: the S0-2 reformat removed it, and zero such lines exist in the file
today. The source-of-truth notice and the `curl`/`grep` hint of FR-31 / D-30 are
therefore an **addition** to the top of the file, not a replacement of an existing
line (D-32).

## 2. Goals

- **G1.** `page/reydavid_experience.md` is the single hand-maintained source for all
  resume-derived content, in a format David could send to a recruiter unchanged.
- **G2.** `profilegen extract` is a repeatable, deterministic compiler:
  source markdown → `data/resume.yaml`, complete output, zero `TODO` placeholders,
  including search stories with auto-inferred tags.
- **G3.** Site-only content (headline, hero stats, nav, branding, palette chrome,
  project card metadata) lives in the template as static content.
- **G4.** One GitHub Actions workflow builds and deploys `page/` to GitHub Pages on
  every push to main, replacing the currently-red `static.yml`.
- **G5.** The template carries the metadata ported from the old site (GA, favicon,
  og:image, canonical, author, keywords).
- **G6.** No toolchain command can destroy the source file.

## 3. Non-goals

- **N1.** No special markup or annotations in the source for stories or tags. The
  file must read as a normal resume. (Revision 2 voided this non-goal; the format
  reversal reinstates it, and with it the ban on `- tags:`, `- status:`, `- href:`
  and `- roles:` KV lines.)
- **N2.** No `site.yaml` or second config file for site-only content. Static content
  lives in the template.
- **N3.** CI never runs `extract`. No LLM or network calls anywhere.
- **N4.** No redesign of the page. Only data wiring, the ported meta tags, and the
  template edits forced by optional model fields (§11, D-21 and D-22: the
  `{{if .Technologies}}` and `{{if .Roles}}` guards).
- **N5.** Extraction need not reproduce today's `data/resume.yaml` byte for byte.
  Approximate reproduction of its content is the bar (§9, AC-2).
- **N6.** No SKILLS-driven extension of the tag dictionary. Cut outright
  (§10, D-14).

### Extract command

- **FR-1** `profilegen extract` reads `page/reydavid_experience.md` by default
  (`-in`) and writes `data/resume.yaml` by default (`-out`). The `-force` flag and
  the "`-in` is required" check are removed. Extract runs locally only.
  *Acceptance:* `go run . extract` with no flags succeeds from a clean checkout.
- **FR-2** Extract output is **complete**: every field build consumes is populated
  from the source or by inference. No `TODO` or equivalent placeholder appears in
  the output. Re-running regenerates the file without friction.
  *Acceptance:* `grep -c TODO data/resume.yaml` is 0.
- **FR-3** Extract is **deterministic**: the same input produces a byte-identical
  `data/resume.yaml` on every run (stable ordering, no timestamps, no randomness).
  *Acceptance:* AC-1.
- **FR-4** The generated YAML satisfies build validation (`model.go:131-138`):
  `profile.name` non-empty, every story has a title and at least one tag, plus the
  suggestions floor of FR-28.
  *Acceptance:* AC-4.
- **FR-5** The generated YAML carries a header comment stating it is
  machine-generated from `page/reydavid_experience.md` and must not be hand-edited.
  The current header (`data/resume.yaml:1-4`), which calls the YAML the source of
  truth and claims build emits the markdown, is replaced.
- **FR-27** **Extract validation gate.** Before writing any output, extract
  validates the in-memory result: `profile.name` non-empty, at least 1 experience
  entry, at least 1 story, every story titled and with at least 1 tag,
  `search.suggestions` between 1 and 8 inclusive. On any failure it prints the
  failed check to stderr, exits non-zero, and leaves `data/resume.yaml` untouched.
  *Acceptance:* AC-9.
- **FR-36** Extract prints a one-line summary including a count of skipped or
  warned lines, so a silently degraded parse is visible.
  *Acceptance:* running extract on a source with one malformed entry line reports
  a non-zero warning count on stderr.

### Source format (input contract)

- **FR-6** **The parser implements the §6 Part B tolerance contract, not an exact
  shape.** Structure is recognized by heuristics (H-1 to H-8): heading level,
  emphasis, dash variant, date placement, bullet marker and section-name suffixes
  may all vary without a code change and without David normalizing the file. The
  canonical baseline of §6 Part A is one member of the accepted structural family,
  not the definition of it. Tolerance is bounded and mechanical: parsing stays
  deterministic and offline (AC-1, NFR-02), so no LLM, no network and no
  probabilistic scoring may be used to absorb drift.
  *Acceptance:* the FR-37 golden-fixture suite, which is the executable spec of this
  contract, passes on the baseline file and on every drift fixture it carries.
- **FR-7** Sections map to output as follows:
  - `SUMMARY` → `hero.bio_html` (FR-44).
  - `EXPERIENCE` → experience entries + one story per achievement bullet.
  - `EDUCATION` → education entries (institution, detail, years).
  - `CERTIFICATIONS` → certifications list.
  - `SKILLS`, `LANGUAGES` → parsed without error; no render target in v1
    (§11, D-26). They do **not** feed the tag dictionary (N6).
  - Optional story-producing sections, present in the reformatted source and parsed
    like EXPERIENCE bullets (§11, D-20): `SPEAKING & TEACHING` (source slug
    `community`), `OPEN SOURCE` (slug `open source`), `HOMELAB` / `PROJECTS` (slug
    derived from the project name, for example `tempura`).
- **FR-8** Unknown sections must not crash extraction. Skip them and note it on
  stderr.
- **FR-43** **The source is reformatted by hand, once. Landed.**
  `page/reydavid_experience.md` has been rewritten from its machine-written KV
  format into the §6 recruiter format: 114 lines, described as committed in §6
  Part A (D-32). This is a content deliverable, not a code deliverable, and it is a
  prerequisite for FR-6 and AC-2. The reformat carried the curated story texts of
  today's `data/resume.yaml` over as achievement bullets and added further ones: the
  committed file yields **42** story-producing bullets (D-34). Two content edits
  remain, both content-side and both listed in D-35: education years plus the
  `Universidad de Guadalajara` entry, and per-entry `Technologies:` lines. Authored
  as a content deliverable and reviewed by David (§11, D-29).
- **FR-44** The source gains a `SUMMARY` section. Its prose becomes `hero.bio_html`,
  with `**bold**` converted to `<strong>` and nothing else escaping as markup.
  *Acceptance:* the rendered hero paragraph shows the same bolded phrases as
  `data/resume.yaml:24-30` renders today.

### Search stories and tag inference (reinstated)

- **FR-9** Every achievement bullet under an EXPERIENCE entry or an FR-7 optional
  section becomes one story:
  - `title`: the bullet text up to the first `.`, `:` or spaced `—`, trimmed; if the
    result exceeds 60 runes it is cut at the last word boundary at or below 60 and
    `…` is appended. Truncation is **rune-safe**, never mid-rune
    (`extract.go:192-199` is byte-based today and must be converted). When two
    stories condense to the same title, the later one gets its source slug appended
    in parentheses. The rule is fully deterministic (§11, D-27).
  - `story`: the bullet text.
  - `source`: the slug of the entry's company, or the section's slug for the FR-7
    optional sections.
  - `href`: the first URL found in the bullet prose, else `#experience` (FR-45).
  - `tags`: auto-inferred (FR-10).

  This requirement is **unconditional** (§11, D-34): there is no bullet-selection
  rule, no cap and no curation step. The story count is a consequence of the source,
  not a target.
- **FR-10** Tags are inferred with **no markup in the source**, from three inputs
  (details in §7): a technology dictionary, a theme keyword mapping, and the entry
  slug.
- **FR-20** Every story ends with at least one tag. The entry slug guarantees this
  floor.
- **FR-21** The dictionary and the theme mapping live in the toolchain (Go code or a
  repo data file, architect's choice), never in the source markdown.
- **FR-45** **Story hrefs.** A story's href is the first URL matched in its bullet
  prose (markdown link target or bare URL, with trailing punctuation trimmed),
  defaulting to `#experience` when the bullet contains none. This is also where
  project story hrefs come from, since project cards are static template HTML
  (§11, D-23). Consumer contract:
  `template/index.html.tmpl:664-665` branches on `href.startsWith('#')`, anchors
  scroll and everything else opens in a new tab.
- **FR-11** Suggestion chips: `search.suggestions[0]` is **pinned** to
  `performance`. The remaining entries (up to 7 more, 8 total) are the most frequent
  inferred tags across all stories, excluding tags that are also story source slugs
  and excluding `performance` itself. Computed at extract time and stored in
  `search.suggestions`.
- **FR-22** Chip ordering and tie-breaking are deterministic (frequency descending,
  then alphabetical).
- **FR-28** **Suggestions floor.** `search.suggestions` always contains 1 to 8
  entries. Both extract (FR-27) and `LoadResume` reject an empty list, because
  `template/index.html.tmpl:443` indexes element 0 during template execution and
  `:683` indexes it again in browser JS.
  *Acceptance:* a YAML with `search: {suggestions: []}` makes build exit non-zero
  with a validation message, not a template error.
- **FR-30** **Banner keyword.** `search.suggestions[0]` renders as the visible
  typewriter keyword in the hero banner (`template/index.html.tmpl:443,681-695`).
  **Decision recorded: pinned to `performance`** (FR-11), preserving today's banner
  and removing the frequency-ranking risk that it would flip to `go`.

### Build command

- **FR-12** `profilegen build` renders the committed `data/resume.yaml` plus

  error, no runtime error, zero results).

  and no Makefile target may create, modify or delete `page/reydavid_experience.md`.
  Build writes exactly one file into its output directory: `index.html`.

## 6. Source format: tolerant parser contract

This section has two parts, and the split is deliberate (§11, D-31):

- **Part A is descriptive.** It documents the canonical baseline, David's master
  resume as committed at `page/reydavid_experience.md`. It is an example of the
  accepted format, not a specification of it. Nothing in Part A is a parser
  requirement, and the file may drift away from this description over time.
- **Part B is normative.** It is the parser contract: the heuristics H-1 to H-8 plus
  the retained rules P-6 to P-8. The parser must accept any file in the same
  structural family as Part A, absorbing drift (heading level, emphasis, dash
  variant, date placement, bullet marker, section-name suffix) **without code
  changes**. Tolerance is mechanical and bounded: parsing remains deterministic and
  offline (AC-1, NFR-02).

### Part B: normative tolerance rules

- **H-1 Sections are matched by leading keyword.** A line is a section header when it
  is a markdown heading at **any** level (`##`, `###`, and deeper) whose text, with
  emphasis markers stripped, **begins** with a known section keyword, compared
  **case-insensitively**. Text after the keyword is tolerated and ignored, so
  `### HOMELAB / SELF-HOSTED INFRASTRUCTURE`, `## Homelab`, `### **HOMELAB**` and
  `### Homelab & Lab Notes` all map to the HOMELAB section. Bold-only headers with no
  `#` marker are also accepted when they consist solely of a bold upper-case keyword
  on their own line. A heading whose keyword is unknown starts an unknown section:
  skip and warn, never crash (FR-8 unchanged).
- **H-2 The identity block is everything before the first section header.** Within
  it:
  - `profile.name` is the **first non-empty line**, whether bold, plain, or an H1.
    Emphasis and `#` markers are stripped.
  - If that line itself contains a spaced separator (`—`, `–`, `-`, `•`, `·`), it is
    split once: left of the separator is the name, right of it is the role line. This
    is the D-25 `# Name — Role Line` shape, which stays parseable as a degenerate
    one-line identity block.
  - Otherwise `hero.role_line` is the **next line containing separator characters**
    (`•`, `—` or `·`), taken **verbatim**, no splitting, no re-ordering.
  - Any line containing contact links (markdown links, `mailto:`, bare URLs, an email
    address) is **ignored** (D-24).
- **H-3 Entries are a bold-ish line plus a nearby date.** A line is an entry line
  when it is bold or **partially** bold (`**Company** – Title – Location` counts) and
  a **date-looking line follows within two non-blank lines**. The date may sit:
  - on the entry line itself (`**Company – Title – Location – Apr 2024 – Present**`);
  - on a following *italic* line (`*Apr 2024 – Present*`);
  - on a following **plain** line (`Apr 2024 - Present`).

  Date-range extraction **always runs on the raw text before any dash splitting**,
  and the matched span is stripped before the remainder is split (this is P-1's
  substance, retained). Rationale: the separator pattern (`\s+[–—-]\s+`) matches the
  dash *inside* a date range, so splitting first shatters `Apr 2024 – Present` into
  two segments and pushes `Apr 2024` into the location field. The same bug applies to
  education year spans (`2009 – 2014`).

  Range separators tolerate all three dash variants (`-`, `–`, `—`). A **trailing
  parenthetical is tolerated and discarded**: `Aug 2025 (1-week engagement)` parses as
  the range `Aug 2025` to `Aug 2025` and the parenthetical text is dropped, not
  stored anywhere. Recorded explicitly so no one re-adds it as a field later.
  `Present` (and equivalent current wording) marks the ongoing role
  (`Experience.Current()`, `model.go:80`).
- **H-4 The entry line remainder splits on spaced dashes, arity-tolerantly.** After
  the date span is stripped (H-3), the remainder is split on spaced dashes (`-`, `–`,
  `—`; only *spaced* dashes separate, so `open-source` and `C#-based` survive) into:
  - 3 segments → company, title, location;
  - 2 segments → company, title, with an empty location;
  - 1 segment → company, with title and location empty;
  - 4 or more → the first is company, the last is location, the middle segments are
    rejoined as the title.

  Ambiguous arity **warns and continues** (FR-36), never fails. Dropping an entry is
  worse than filing one field imperfectly, and FR-27 is the aggregate backstop.
- **H-5 Bullets accept any marker and any indentation.** `*`, `-` and `+` are all
  bullet markers, at any consistent indentation depth (nested bullets are flattened
  into their parent entry). A bullet is attached to the most recent entry, or to the
  current section when the section is a bullets-only story section (FR-7).
- **H-6 Story titles.** If the bullet starts with a **bold prefix ending in a colon**
  (`**The Translator Pattern:** ...`), that prefix is the story title (bold markers
  and the colon stripped) and the remainder is the story text. Otherwise the
  condensed-first-clause rule applies unchanged: bullet text up to the first `.`, `:`
  or spaced `—`, with the FR-9 / D-27 truncation and de-duplication rules.
- **H-7 Optional `Technologies:` line.** A plain line whose first token before the
  colon is `technologies`, matched **case-insensitively**, closes an entry. Its value
  is parsed **verbatim** (order and casing preserved, split on commas) into that
  entry's technologies (§11, D-21). When absent, technologies are inferred from the
  entry's bullets. The template guards with `{{if .Technologies}}`, so an entry with
  neither renders no chip row.
- **H-8 Graceful degradation everywhere.** Trailing whitespace, blank lines between
  entries, minor punctuation variance and an unrecognized line never abort the parse.
  Every rule above degrades the same way: **skip, warn, count** in the FR-36 summary
  line. The aggregate result is still gated by FR-27, so a wholesale parse failure
  exits non-zero rather than shipping a gutted site. A parser that silently produces
  an empty section is a bug; a parser that warns and produces a partial section is
  the contract.

Retained rules, unchanged by this restructuring:

- **P-6 Bare URL matching trims trailing punctuation.** `see https://x.com/y.`
  yields `https://x.com/y`, not a href ending in `.`. Trim trailing `.,;:!?)]`.
- **P-7 Rune-safe truncation.** Story-title truncation operates on runes, never on
  bytes. The data is full of multi-byte characters (`—`, `·`, `í`,
  `Instituto Tecnológico`), and byte slicing emits invalid UTF-8.
- **P-8 Roles are derived from the job title.** `Experience.Roles` stays in the
  model (§11, D-22, which reverses the "roles dropped" consequence of D-01). Roles
  come from a role-keyword mapping applied to the title segment of the entry line
  (architect, full-stack, back-end, people manager, security tooling, consultant,
  speaker, ...), so `Software Architect / Full Stack Developer` yields `architect`
  and `full-stack`. The approximation is accepted; an entry whose title yields no
  roles renders no badges, guarded by `{{if .Roles}}` in the template.

**P-1 to P-5 are FOLDED**, retained as stubs so the numbers are not silently reused
and so D-15's cross-reference still resolves: P-1 (date extraction before dash
splitting) → H-3; P-2 (partially bold entry lines) → H-3; P-3 (dash tolerance) →
H-3 and H-4; P-4 (inline dates) → H-3; P-5 (`Present` marks the current role) → H-3.

   `data/resume.yaml` are the census to extend it from.

   Matching rules:
   - **T-1** Default matching is case-insensitive on word boundaries.
   - **T-2 Ambiguous short aliases match case-sensitively and exactly**: `go`, `ai`,
     `c`, `r`. Case-insensitive `\bgo\b` tags every bullet containing the English
     verb ("go live", "go from 1K to 40K"), inflating the tag on false positives.
   - **T-3 Custom word boundaries on both sides** for `c#`, `c++` and `.net`. `\b`
     fails on the right of `#`, `+` and on the **left** of `.` (a space followed by
     a dot is two non-word characters, so `\b\.net` never matches at all).

2. **Theme keyword mapping.** Trigger words map to theme tags:

   | Trigger words in bullet | Tag |
   |---|---|
   | throughput, faster, Nx (e.g. "40x"), optimized | `performance` |
   | rewrote, replaced, migration | `migration` |

   | manager, mentored, 1:1s, interview, speaker, talks | `leadership` |
   | open source, contribution, merged | `open-source` |
   | debugged, root-caused, traced, bug | `debugging` |
   | goroutine, parallel, concurrency | `concurrency` |

3. **Entry slug.** The story's company or section slug is added as a tag, which is
